# Работа с Git worktree

Читай эту инструкцию при подготовке, восстановлении или завершении worktree.
Worktree изолирует файлы. Ветки, refs и часть настроек Git остаются общими.

## Выбери окружение

1. Определи корень исходного проекта.
2. Определи путь документов задачи.
3. Прочитай применимые `AGENTS.md`.
4. Прочитай проектную инструкцию worktree.
5. Проверь параметры проектного скрипта подготовки worktree.
6. Проверь `git status --short --branch`.
7. Проверь `git worktree list --porcelain`.
8. Проверь ветку задачи, базовую ветку и upstream.
9. Проверь незавершённые Git-операции через служебные пути Git.

У linked worktree `.git` является файлом.
Не определяй состояние операций по пути `.git/MERGE_HEAD`.
Не переноси соглашения другого проекта по сходству имён.
Если worktree задачи существует, проверь его состояние перед продолжением.
Оставь незакоммиченные изменения исходной папки на месте.
Не убирай эти изменения через stash или reset.
Не переноси эти изменения автоматически.

## Проверь базу новой ветки

1. Проверь базу, которую требует проект.
2. Сохрани исходный SHA задачи.
3. Проверь актуальность базы относительно сервера в пределах разрешённых действий.
4. Если проверка сервера недоступна, укажи это ограничение.

Совпадение с локальной remote-tracking ref не подтверждает актуальность сервера.
Выполняй fetch только в пределах разрешения проекта и пользователя.

Если требуется обновить основную ветку, соблюдай проектный порядок.
Перед обновлением проверь чистоту дерева.
Проверь отсутствие незавершённых Git-операций.
Согласуй целевой SHA.
Обновляй ветку только через fast-forward.
Не переключай основную папку с чужими изменениями или занятой веткой.
При расхождении истории останови подготовку.
Не применяй reset или rebase для устранения расхождения.

## Создай worktree

Если проект содержит скрипт подготовки worktree, используй этот скрипт.
Сначала выполни предварительную проверку, которую предоставляет скрипт.
Не заменяй скрипт командой `git worktree add`.
Скрипт может настраивать sparse-checkout, инструкции и инструменты.
Если скрипта нет, используй штатные команды Git по правилам проекта.

### Пример для `scripts/task-git.ps1`

Сначала проверь поддержку этих режимов в текущем скрипте и проектной инструкции.
Подставь проверенные значения вместо аргументов в угловых скобках.
Пути с пробелами заключи в кавычки.
Для существующей ветки добавь `-ReuseBranch` в обе команды.

Из исходной папки выполни предварительную проверку:

```powershell
powershell.exe -NoProfile -NonInteractive -File scripts/task-git.ps1 -Mode PlanWorktree -Task <slug> -TaskDirectory <существующий-путь-документов>
```

После успешной проверки создай worktree:

```powershell
powershell.exe -NoProfile -NonInteractive -File scripts/task-git.ps1 -Mode StartWorktree -Task <slug> -TaskDirectory <существующий-путь-документов>
```

Имя ветки и каталог определяет скрипт.
Не сбрасывай существующую ветку.

В пилоте СММ инструкция находится в `scripts/README-worktree.md`.
Пилот использует ветки `task/<slug>`.
Документы остаются в исходном каталоге.
Не применяй эти соглашения автоматически к другим проектам.

## Проверь новую папку

1. Используй полученный абсолютный путь для последующих команд.
2. Проверь ветку и HEAD.
3. Если есть манифест подготовки, проверь его содержимое.
4. Проверь sparse-checkout.
5. Проверь инструкции и профиль инструментов.
6. До подключения workspace MCP проверь [базовый индекс и слой изменений](search-index.md).
   Если повторное использование не подтверждено, оставь workspace MCP остановленным.
   Продолжай независимые проверки остальных сервисов.
7. Проверь корень workspace анализатора.
8. Проверь готовность нужных подсистем анализатора.
9. Проверь принадлежность wiki к исходному проекту.

Локальные настройки могут копироваться снимком без дальнейшей синхронизации.
Наличие `.mcp.json` или `.codex/config.toml` не подтверждает подключение клиента.
При ошибке одной подсистемы используй готовые подсистемы.
Укажи ограничения анализа.
Не очищай кеш без установленной причины.
Не перестраивай индекс без установленной причины.
Не выдавай индекс исходной папки за индекс изменяемого worktree.
Используй RLM по проектному профилю.
Веди документы в одном согласованном месте.
Не создавай копию проектной wiki для каждой задачи.
Создание worktree не назначает базу 1С.
Не копируй auth-файлы, токены или подключения из основной папки.

## Восстанови подготовку после ошибки

1. Проверь созданную папку, ветку и манифест.
2. Сохрани результат подготовки.
3. Выясни причину ошибки.

Не удаляй созданные файлы и ветку автоматически.
Не повторяй создание поверх существующего окружения.

## Доставь и закрой задачу

Сравнивай результат с сохранённой базой задачи.
При изменении основной ветки не подменяй базу задачи молча.
Для повторной доставки учитывай фактически поставленные коммиты.

Без подтверждённой поддержки linked worktree не запускай старый `task-close.ps1`.
Обновляй основную папку отдельно от завершения worktree.
После корпоративной выгрузки сверь изменённые объекты и сопутствующие файлы.
Разные SHA сами по себе не означают различие содержимого.
Сохрани документы, которых нет в выгрузке.

Перед разрешённым удалением проверь:

- незакоммиченные изменения;
- неотслеживаемые файлы;
- нужные ignored-файлы;
- сохранность коммитов;
- место сохранения документов.

Для принудительного удаления получи явное разрешение.
