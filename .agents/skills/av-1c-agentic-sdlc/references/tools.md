# Навыки, MCP и постоянная память

Имена профилей, пути и ограничения бери из правил проекта.
Если нужный инструмент недоступен, укажи это в результате работы.
Продолжай шаги, для которых есть доступные источники.

## Выбери навык или MCP

| Задача | Инструмент |
|---|---|
| Получить постановку | Jira через Atlassian MCP |
| Найти документацию Confluence | OpenViking |
| Уточнить API платформы | `bsl-reference` |
| Найти и проверить код | Workspace `bsl-analyzer` текущей папки |
| Проверить применённые метаданные, SDBL или журнал ИБ | Live-подключение `bsl-analyzer`; прочитай [live-1c.md](live-1c.md) |
| Дополнить неполный анализ | RLM, если он разрешён в проекте |
| Получить общие знания и предпочтения | `llm-wiki-personal` |
| Получить знания проекта | `llm-wiki-project` |
| Написать или проверить BSL | `1c-dev-standards` |
| Изменить XML, метаданные, формы, роли или СКД | Профильные навыки `cc-1c-skills` |
| Доработать EPF/ERF с регистрацией БСП | `av-1c-external-bsp` и профильный навык `cc-1c-skills` |

Читай выбранный навык до выполнения его операций.
Если профильный навык недоступен, сообщи об ограничении.
Перед вызовом скрипта `cc-1c-skills` прочитай его `--help`.
Установленная версия может использовать Python вместо старых PowerShell-скриптов.

При переносе изменений через `cc-1c-skills` проверь параметры установленного скрипта:

- В `db-load-git` задай `ConfigDir`, `Source` и `CommitRange`.
- Для проверки списка поставки используй `DryRun`, если он доступен.
- При загрузке расширения проверь `Extension` и сопутствующие файлы.
- В `db-load-xml` используй `Mode Partial` с `Files` или `ListFile`.
- Файл `ListFile` должен содержать относительные пути в UTF-8 BOM.
- У `db-load-xml` и `db-update` нет `DryRun`.
- После отказа Partial не переходи на Full.
- `db-update` отдельно применяет конфигурацию БД.
- Проверь параметры `Extension`, `WarningsAsErrors` и `StrictLog` по `--help`.
- Флаг `UpdateDB` у загрузчика требует разрешения на загрузку и обновление БД.

Диапазон `CommitRange` определяй по фактически доставленному состоянию dev.
Для первой поставки укажи исходный и поставляемый коммиты ветки.
Записывай диапазон и результат проверки в документы задачи.

Jira определяет требования с учётом согласованных уточнений.
Актуальный код и проверки в базе подтверждают поведение.
Wiki и Confluence дают контекст.

## Проверь исходники

1. Выбери workspace текущего проекта или worktree.
2. Проверь `status` нужных подсистем и фактические корни.
3. Если место реализации неизвестно, начни с `search_code`.
4. Если семантика готова, используй семантический поиск.
5. Если семантика не готова, используй лексический поиск.
6. Уточни результат через `outline`, `symbol_info` и `metadata`.
7. Проверь связи через `references` и `graph`, если эти подсистемы готовы.

Исследуй основную конфигурацию и расширения вместе.
Учитывай перехваты методов.
При `loading` или `not_ready` продолжай работу через готовые подсистемы.
Позже повтори проверку нужной подсистемы.
При `failed` исследуй ошибку.
Не скрывай отказ увеличением таймаута или повторными перезапусками.

Перед выводом об отсутствии связи проверь `root_id`, `freshness` и `completeness`.
Проверь усечение выдачи и доверие к рёбрам графа.
Пустой ответ анализатора или RLM не доказывает отсутствие связи.
Готовность лексики не подтверждает готовность семантики или графа.

До изменения сохрани диагностики затрагиваемых файлов.
После связного изменения повтори `diagnostics file` для тех же файлов.
Проверь изменённые запросы через `query validate`.
При изменении интерфейсов или связей повтори `graph` и `references`.
Сравнивай результаты при одинаковой области и полной выдаче.
Без настроенного baseline используй `diagnostics workspace` как обзор.
Не считай такой обзор блокирующим критерием.

`diagnostics` проверяет файлы workspace.
Он не проверяет внешний файл вне индекса.
Не подменяй такую проверку BSL Language Server без основания и правил проекта.

## Используй RLM при неполном покрытии

Если `bsl-analyzer` недоступен или его покрытия недостаточно, используй разрешённый RLM.
Исследуй CF и расширения вместе.
Уточняй API через help. После работы закрывай сессию.
При обновлении индекса используй корень и конфиг работающей службы.
Не создавай отдельный пользовательский кеш вместо служебного индекса.
После обновления проверь корень, актуальность и commit.

## Отделяй статическую проверку от выполнения

HTTP-расширение предоставляет метаданные ИБ, проверку и выполнение SDBL,
проверку BSL snippet, выполнение BSL и чтение журнала регистрации.
Настройка, выбор подключения и границы действий описаны в [live-1c.md](live-1c.md).

`execute(action=check)` проверяет синтаксис через HTTP или настроенный native executor.
Он не выполняет проверяемый код как `run` или `eval`.
Проверка module требует native executor; наличие HTTP-сервиса её не обеспечивает.
`execute(action=run|eval)` выполняет произвольный BSL в ИБ.
Вызывай его только для задачи, которой требуется выполнение кода.
Сначала проверь подключение и разрешение на выбранную тестовую ИБ.
Записи, удаления, загрузки и обновление БД требуют разрешения в нужном объёме.
Наличие MCP-сервера такого разрешения не даёт.
Статический анализ не подтверждает поведение при выполнении в 1С.

## Используй постоянную память

В pi память предоставляет плагин `npm:@zosmaai/pi-llm-wiki`.
Не подключай к pi дублирующие MCP `llm-wiki-personal` и `llm-wiki-project`.
Для Codex и Claude Code используются отдельные MCP этих wiki.
Перед записью в pi проверяй фактически выбранный vault инструментами плагина.
Не считай отсутствие MCP wiki отсутствием памяти в pi.

В начале задачи вызови `wiki_recall`.
При необходимости используй `wiki_search` и чтение страницы.
Перед каждой записью выбери персональную или проектную wiki.
Проверь выбранный сервер через `wiki_status`.
Не полагайся на автоматически выбранную wiki.

В проектную wiki записывай знания конкретного проекта.
В персональную wiki записывай общие приёмы, инструменты и предпочтения.
Если вывод содержит обе части, раздели их и свяжи ссылками.
Перед созданием страницы выполни `wiki_search`.
Для важного наблюдения используй `wiki_observe`.
Для повторно используемого вывода используй `wiki_retro`.
Сохраняй подтверждённое решение, его причину и ограничения.
Не сохраняй секреты и пересказ переписки.
Каталоги `raw` и `meta` изменяй только инструментами движка.
Если цель записи неоднозначна, уточни её у пользователя.
Если запись не удалась, сообщи об этом.

В worktree используй wiki исходного проекта.
Не создавай отдельную копию wiki задачи.

## Найди документацию Confluence

Перед анализом реализации выполни поиск OpenViking.
Укажи проект, объект и действие из постановки.
Используй `find` или `search` в URI корпуса из правил проекта.
Для `search` укажи `mode="list"`.
Прочитай найденный документ через `read`.
Для ссылки используй исходный URL Confluence из frontmatter.
Сверь сведения с Jira, актуальным кодом и проверками.
Пустой результат не доказывает отсутствие документации.
Если OpenViking недоступен, укажи, что документация не проверена.

Используй OpenViking только для выбранных материалов Confluence.
Переписку, предпочтения и состояние задач храни вне OpenViking.
Импортируй или обновляй только материалы, которые выбрал пользователь.

Для настройки подключений прочитай [mcp.md](mcp.md).
