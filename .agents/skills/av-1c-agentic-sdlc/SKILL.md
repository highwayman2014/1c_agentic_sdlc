# Работа над задачей 1С

Применяй правила текущего проекта. Соблюдай разрешения пользователя.
Пути, ветки, скрипты, базы и порядок доставки определяет проект.

Пиши короткими предложениями. Давай одну инструкцию в предложении.
Ставь условие перед действием. Используй один термин для одного понятия.
Эти правила адаптируют принципы ASD-STE100 для русского текста.

## Выбери этап

1. Определи проект и ключ задачи.
2. Определи текущий этап.
3. Проверь уже разрешённые действия.
4. Если задача начата, прочитай её документы.

Если пользователь запросил только анализ, не меняй исходники.
Если пользователь запросил реализацию, выполни анализ и разработку.
Согласовывай план отдельно только по требованию пользователя или проекта.
Если шаг зависит от существенного вопроса, останови этот шаг.
Продолжай независимые шаги.

Для анализа и ревью новая ветка не нужна.
Если EPF/ERF ведутся вне Git, не создавай для них ветку или worktree.

## Выбери рабочую папку

Для изменения исходников выбери обычную ветку в текущей папке или отдельный worktree.
Сначала учитывай выбор пользователя и правила проекта.
Если способ не задан, выбери удобный вариант по состоянию рабочей папки.

| Условие | Подходящий вариант |
|---|---|
| Папка свободна от другой работы; переключение веток не мешает текущей задаче. | Обычная ветка в текущей папке. |
| Нужно сохранить другую работу или выполнять задачи параллельно. | Отдельный worktree. |

Если окружение задачи уже существует, проверь его состояние перед продолжением.
Не создавай второе окружение без необходимости.
Запиши выбранный способ и рабочую папку в `state.md`.

Для обычной ветки проверь status, текущую ветку и незавершённые Git-операции.
Перед переключением проверь незакоммиченные и неотслеживаемые файлы.
Если есть изменения другой задачи, не переноси их переключением ветки.
При таком конфликте используй worktree или уточни дальнейшие действия.
Проверь базовую ветку по правилам проекта.
Сохрани исходный SHA задачи.
Если ветка задачи существует, продолжай её без сброса.
Если ветки задачи нет, создай её от проверенной базы по правилам проекта.
После создания или переключения проверь ветку и HEAD.
Не убирай чужие изменения через stash, reset или удаление.

При подготовке, восстановлении или завершении worktree прочитай [worktree.md](references/worktree.md).
При настройке MCP прочитай [mcp.md](references/mcp.md).

## Подготовь документы

1. Найди каталог по точному ключу Jira.
2. Проверь прежнее расположение документов.
3. Если каталог найден, продолжай работу в нём.
4. Если каталога нет, используй проектное соглашение о пути.

Если соглашения нет, используй `tasks/YYYY-MM/<ключ>-<краткое-имя>`.
Не создавай дубли каталогов. Не переноси историю автоматически.
Для консультации вне конкретной задачи документы не нужны.

| Файл | Содержание |
|---|---|
| `description.md` | Полная постановка Jira со структурой, ссылками и URL. Решения сюда не входят. |
| `plan.md` | Решения, шаги реализации и проверки. |
| `state.md` | Текущий этап, выполненные шаги, следующий шаг, открытые вопросы и результаты проверок. |

Привяжи каждое решение к пункту постановки или строке `description.md`.
Привяжи каждый шаг к пункту постановки или строке `description.md`.
Для уточнения укажи источник и дату.
Опиши правило поведения один раз.
В шагах ссылайся на это правило.
Для шага укажи объекты, файлы, действие и критерий готовности.
Анализ кода запиши в соответствующий шаг плана.

В `state.md` укажи пути рабочей папки и документов, ветку, исходный SHA и ограничения инструментов.
После доставки укажи базу и фактически доставленный диапазон коммитов.
Не записывай секреты.
После ответа на вопрос перенеси решение в план.
Затем убери вопрос из `state.md`.
Если проект требует историю действий, веди `changelog.md`.
Не создавай параллельные планы и заметки без необходимости.

## Выполни анализ и разработку

1. Получи постановку через Atlassian MCP или используй предоставленный источник.
2. Если Jira недоступна, укажи неполноту постановки в `state.md`.
3. Используй wiki и документацию для получения контекста.
4. Определяй требования по постановке и согласованным уточнениям.
5. Проверяй поведение по актуальному коду и результатам проверок.
6. Исследуй основную конфигурацию вместе с расширениями и перехватами.
7. Выбери workspace анализатора для текущей рабочей папки.
8. Проверь корень, актуальность и полноту нужных подсистем.
9. Перед изменением сохрани диагностики затрагиваемых файлов.
10. Выполни шаги плана в согласованном объёме.
11. После связного изменения проверь diff.
12. Повтори диагностики тех же файлов.
13. Проверь изменённые запросы.
14. Проверь затронутые связи.

Для BSL используй стандарты разработки 1С.
Для XML, метаданных, форм, ролей и СКД используй профильные навыки.
Используй RLM по правилам проекта.
Выполняй поиск документации по правилам проекта.
Учитывай ограничения индекса.
Пустой или неполный поиск не доказывает отсутствие связи.
Статический анализ не подтверждает поведение при выполнении в 1С.
Расширяй или повторяй проверки только при наличии причины.

## Выполни ревью

1. Проверь соответствие постановке и плану.
2. Проверь ошибки поведения.
3. Проверь влияние расширений.
4. Оцени достаточность проверок.
5. Запиши результаты и невыполненные проверки в `state.md`.

При существенной неопределённости предложи ревью более сильной моделью.
Укажи причину такого ревью.
Если переключения модели не было, не заявляй о нём.

## Заверши этап

Сообщи, что изменено, что проверено и что осталось.
Отличай готовность к доставке от подтверждённой проверки в ИБ.
Если доставка не подтверждена, укажи это состояние в `state.md`.

Для commit, push, хранилища и доставки соблюдай ограничения проекта.
Проверь разрешение пользователя на каждую требуемую операцию.
Разрешение на одну операцию не разрешает остальные.
В корпоративном проекте не заменяй выгрузку из хранилища локальным слиянием в основную ветку.

Выполняй live-код только в явно разрешённой тестовой ИБ.
Для загрузки конфигурации, обновления БД и изменения данных используй только разрешённый объём действий.
Если разрешения на нужное действие нет, запроси его.
Не копируй секреты и подключения между окружениями.
Удаляй worktree и ветку только по разрешению после проверки сохранности результата.
